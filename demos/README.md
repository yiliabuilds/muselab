# Demonstrations

Six cases, all from real runs. Each states its input, workflow, output, test status and known
deviation. **Nothing here is a mock-up**, and every AI-generated image is marked as such.

> **On image provenance.** All renders in `demos/images/` were produced by an image-generation
> model and carry the host tool's watermark (`AI生成 / WORKBUDDY>`). They are **not** photographs
> of real products and must not be presented as such. The two studio-looking jewelry images are
> synthetic; the face images are generated people, not real individuals.
>
> Reference photographs used during development (a beach aerial, two product photos of pearl
> jewelry) are **not redistributed** in this repository — their provenance is not documented.
> The palette and analysis outputs derived from them are included; the source pixels are not.

## D1 · Pixels → measured palette

| | |
|---|---|
| **Input** | `images/01_input_product_beads_synthetic.png` — synthetic bead strand generated by `tests/make_fixtures.py` (also `01b_input_palette_blocks_synthetic.png`, colour blocks with a ground-truth JSON) |
| **Workflow** | `scripts/color_extract.py` → CIELAB k-means, 8 clusters, area shares; `method=pixel_kmeans` recorded in the output |
| **Output** | `images/02_measured_palette_8.png`, `images/02b_measured_palette_5.png` |
| **Test status** | **Verified** — cases 02/02b: 5/5 known patches recovered, area shares within tolerance; 02e proves the tool says `visual_estimate` instead of inventing a measurement |
| **Known deviation** | At 5 clusters two adjacent greys merge into one; the palette is a summary, not a segmentation |

The point of this case is not the swatches. It is that every swatch carries a measurement method
and a pixel share, so a downstream design step can be held to a number instead of an impression.

## D3 · Jewelry concept render + gate

| | |
|---|---|
| **Input** | `jw_beach_C` v5 (`approved`, frozen), prompt 1058 chars, matched verbatim to the design record |
| **Workflow** | `ImageGen` (1 call, no retry) → `scripts/fidelity_check.py` gate → visual review |
| **Output** | `images/03_jewelry_concept_ai.jpg` (watermarked), `03b_..._clean.jpg` (watermark cropped, 1024×950), `04_jewelry_qa_overlay.jpg` |
| **Test status** | **Failed acceptance.** Gate `verdict=fail`: background max ΔE 24.4 against a spec of ≤6 (a beige cloth with lighting falloff, not the specified seamless neutral). Structure, bead count and material type passed visual review |
| **Known deviation** | Teal stones rendered 9–10 L\* darker than `#128D97` (ΔE 14.1/15.7) — flagged as post-correctable, not a material error. Clasp rendered as an oval link instead of a 4 mm ring; pearl mounted on a wire-wrapped crown instead of a half-drilled pin |

This is a useful failure: the gate separated "wrong background" (hard) from "slightly dark stone"
(correctable) instead of reporting one undifferentiated "looks off".

## D4 · Product fidelity — the model invented what it could not see

| | |
|---|---|
| **Input** | A phone photo of a baroque-pearl bracelet, cropped by the frame at the left and bottom edges |
| **Workflow** | Identify (count beads, sample materials) → fidelity prompt (`product_fidelity`, `input_fidelity=high`) → gate (single-point and multi-point) + visual comparison |
| **Output** | A 1024² product shot |
| **Test status** | **Failed.** Generated image closed the loop, invented the out-of-frame segment, added 2 pink beads, and redrew the clasp and butterfly |
| **Known deviation** | The part of the bracelet outside the photo is unknowable. The model filled it in plausibly — the single most dangerous failure mode for product fidelity, and one no colour gate can catch |

This case is why the gate report has a `needs_human_or_vision` list: counting beads is not a
colour check, and no threshold would have caught it.

## D5 · Makeup: design → render → check → fix the text → render again

| | |
|---|---|
| **Input** | A beach palette → `mk_beach_tidal` makeup spec (nine layers, palette, application steps, prompt) |
| **Workflow** | **v11:** design → one `ImageGen` call → `makeup_check.py` (human-declared ROIs) → visual review. **Then** the stale `concept` was rewritten (v12) and the spec audit gained its concept/prompt checks. **v13:** `makeup_spec_audit.py --strict` (E 0 / W 0) → one `ImageGen` call → gate + review |
| **Output** | `images/05_makeup_render_v11.jpg`, `images/06_makeup_render_v13.jpg` |
| **Test status** | **Both renders failed.** v11: eyeshadow covered the full lid (climb 0.93 on the right eye) and the lower lid was coloured — the spec still contained a stale `concept` line from v1. v13: range corrected (climb 0.31/0.32, lower lid 0.0 % pigment) but hue drifted to 226°/237° against a 192° design — grey-blue instead of grey-teal |
| **Known deviation** | The design asks for a low-chroma grey-teal (C≈9). Both renders returned C 1.8–3.0, i.e. a different colour family. Two iterations of prompt wording did not fix it; the untested route is a reference-image edit |

**The order is worth stating exactly, because it is not the flattering one.** v11 was rendered
*before* any audit could read the `concept` field: the audit existed, but at that point it only
compared colours, and it passed the spec. The failure — full-lid coverage, coloured lower lid — was
found by `makeup_check.py` and by eye, then traced back to a `concept` paragraph still describing
the v1 look, plus an `image_prompt` that had not been synchronised since v8. **The concept and
prompt-contradiction checks were written after that failure**, in response to it. They were then
run on v13 before rendering and reported E 0 / W 0 — and v13 still failed on hue. So the audit
cleared every field it can read and had nothing to say about the one that broke: two instruments,
two blind spots, both documented rather than smoothed over.

## D6 · QA overlays — what the checks actually look at

| | |
|---|---|
| **Input** | The v13 render + human-declared ROIs |
| **Workflow** | `makeup_check.py --overlay`; separate diagnostic crops with reference lines |
| **Output** | `images/07_makeup_qa_roi_overlay_v13.jpg` (ROI boxes), `08/08b_makeup_lid_guides_*_v13.png` (brow edge / lid midpoint / lash line), `09_makeup_under_eye_check_v13.png` |
| **Test status** | **Verified as an instrument, not as an approval.** The overlay shows where the numbers came from; the lid guides show why "it reaches the brow" was wrong on first look (that was brow shadow) |
| **Known deviation** | Boxes are hand-placed. The first attempt put the eyelid band on the lashes, which inflated coverage from 0.24 to 0.46 — dark neutral lashes differ from skin in a\*/b\* too. The band must stop 1–2 px above the lash roots |

`10_fixture_lid_asymmetry_synthetic.png` is the synthetic counterpart: a deliberately asymmetric
lid used by the test suite, included so the check can be inspected without any real face.

## What these six cases do and do not show

They show a pipeline that measures, records, renders, checks its own output and reports what it
could not verify. They do **not** show a system that reliably produces on-spec renders: 0 of 4
real renders passed acceptance. The value demonstrated is in the containment, not the hit rate.
